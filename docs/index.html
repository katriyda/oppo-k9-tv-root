OPPO K9 电视 root 指南

OPPOCNM632 · m7332(MT9632)· Android 9 · 内核 4.9.118(32 位用户态)

可按需取 root(uid=0 + 满 capability) 无监听端口 / 无常驻进程 默认 Enforcing /system 无改动

快速开始

前提:PC 与电视同一局域网,已装 adb。

  1. 连接电视 
    adb connect :5555
  2. 放开 SELinux(约 40 秒,设备每次重启后需要跑一次) 
    adb shell 'dumpsys tvapisvc -cmd "sh /sdcard/r1.sh"'

    验证:adb shell getenforce → Permissive

  3. 终端直取 root 
    adb shell                    # 进入电视
$ sh /data/local/tmp/su.sh   # 交互 root shell,exit 即回普通 shell

    单条命令形式:adb shell 'sh /data/local/tmp/su.sh id'

整个过程不创建监听端口、不留常驻进程;用完即失效。需要 root 时再跑一遍即可。

原理

① 核心原语:内核物理内存读写

设备遗留了 MStar 的 mpool 调试驱动 /dev/malloc,权限 crw-rw-rw-(任何 uid 可打开)。通过 ioctl 指定总线物理地址段,再用 mmap 映射,即可把 DRAM 当作普通数组读写——包括内核数据区。

struct mpool_info { u64 addr, size, interval; u8 miusel, pad[7]; };  // 32 字节
ioctl(fd, 0x80204d04, &info);   // MPOOL_IOC_SET
p = mmap(NULL, size, PROT_READ|PROT_WRITE, MAP_SHARED, fd, 0);
// 映射偏移 = 总线地址 - 0x20000000

已验证地址:init_cred 0x2122d590、enforcing 0x2137bdfc、init_task 0x2121a880

② 提权:patch 自己的 cred

进程身份由内核里的 cred 结构决定,前 8 个字段连续排列:

uid  gid  suid  sgid  euid  egid  fsuid  fsgid

扫描内存找"连续 8 个等于本进程 uid"的位置,改为 0、securebits 置 0、capability 置满,然后立即 getuid() 自证:

  • 返回 0 → 命中自己的 cred,成功;
  • 不是 0 → 改到了别的同 uid 进程,逐字节还原后继续扫。

这个"patch→自证→失败回滚"让扫描本身是安全的,不会误伤其它进程。

③ SELinux:只改一个标志位

UNIX 权限之外还有 SELinux 强制访问控制——这就是早期"uid=0 却什么都不能干"的原因(域受限)。本方案只把全局 enforcing 标志位写 0,不改策略、不加规则、不加载模块;效果易失:重启或 setenforce 1 即恢复。

④ 代码注入链:两步借道

每个 SELinux 域能执行的文件是钉死的,所以要分两步"借道":

1 · PC adb shell域 shell,uid 2000
dumpsys tvapisvc -cmd
2 · com.heytap.tvapiservice域 system_app,uid 1000,可执行任意 shell
CLASSPATH jar + app_process
3 · 在 system_app 域内运行任意 dex策略允许 appdomain 执行 zygote_exec(execute_no_trans)
System.load
4 · 载体 APK 的 lib 目录apk_data_file — system_app 唯一可执行的位置(APK 仅 12.7KB)
8×1000 cred patch + enforcing=0
5 · 全局 Permissiveshell 域自身无 /dev/malloc 权限,必须借这一步打开门
sh /data/local/tmp/su.sh
6 · shell 域进程 8×2000 cred patch/data/local/tmp 对 shell 域可执行,无需 APK
ProcessBuilder inheritIO
7 · 你的终端就是 uid=0不再 fork 任何服务

为什么必须这么绕

约束(来自 SELinux 策略)后果
shell 域对 /dev/malloc 无 allowEnforcing 下 adb shell 自己开不了 malloc → 必须先做 Step 1
appdomain 可执行 zygote_execapp_process 可在调用者自己的域里跑任意 dex

dumpsys 通道按空格裸分词复杂命令必须写成脚本再用 sh 脚本 调用

常见问题

su.sh 输出 uid=2000,不是 0

Step 1 没生效(或设备重启过)。重跑 Step 1,确认 getenforce 为 Permissive 后再执行 Step 2。

Step 1 没有任何输出 / 报错

/sdcard/r1.sh 或 /sdcard/main2.jar 丢失,按 session 目录里的配方用 adb push 补回即可。

重启后要做什么

从"快速开始"第 1 步重跑即可;设备默认回到 Enforcing,且不会有任何 root 残留。

能否开机自动获得 root

刻意不做。10-29 尝试过改 rootfs 做持久化,因 cp 覆盖破坏了 /system/bin/adbd 的 SELinux 标签,重启后 adbd 崩溃循环、设备远程失联。详见 docs/04-history.md。

为什么不用 4445 那种 root 服务

无鉴权监听端口等于给局域网留后门。现在改为让当前终端进程自身变 root(inheritIO 接管终端),用完退出即无痕。

边界与风险

能力:uid=0 + 满 capability + 可改 SELinux 状态 + 可 mount -o remount,rw / 写 rootfs。

限制:cred patch 只作用于该进程及其子进程,退出即消失;enforcing 位易失;SELinux 域仍是 shell,恢复 Enforcing 后域策略照旧生效。

风险:本质是直接写内核物理内存,地址写错可能 panic 或损坏存储(故只用已验证地址段 + 自证回滚)。平时 5555 网络 ADB 常开,同网段任何人可获得 shell 权限,不用时建议关闭。
